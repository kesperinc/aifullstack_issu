1. RHOAI Pod 구성 시 필수 핵심 파라미터

💡 OpenShift AI와 일반 Kubernetes Pod의 결정적 차이

RHOAI 환경은 Red Hat 특유의 보안 제약(SCC), GPU 전용 스케줄링 Taint, 대규모 모델 메모리 매핑(/dev/shm), 수십 GB 가중치 로딩 시간(StartupProbe)을 반드시 사전에 지정해야 CrashLoopBackOff나 OOM 장애를 방지할 수 있습니다.

설정 영역 매니페스트 파라미터 권장 설정값 미설정 시 발생하는 장애 현상
GPU 가속기 할당 resources.limits.nvidia.com/gpu requests와 limits 수량을 1:1로 동일하게 선언 K8s 스케줄러가 GPU 리소스를 인식하지 못하거나 파드 Pending
노드 스케줄링 tolerations, nodeSelector key: nvidia.com/gpu, operator: Exists GPU 워커 노드의 Taint로 인해 파드가 CPU 노드로 튕기거나 배치 거부
공유 메모리 확장 ⭐ volumes.emptyDir.medium: Memory /dev/shm 마운트, 최소 8Gi ~ 32Gi 할당 PyTorch 분산 텐서 병렬(TP) 통신 시 Bus error (OOM) 크래시
보안 컨텍스트 securityContext runAsNonRoot: true, drop: [ALL] OpenShift restricted-v2 SCC 위반으로 파드 생성 차단
LLM 헬스체크 ⭐ startupProbe initialDelaySeconds: 30, failureThreshold: 60 모델 VRAM 로딩 중(3~10분 소요) Liveness 실패로 무한 재기동 루프
가중치 스토리지 volumes (PVC / S3 Secret) RWX 공유 볼륨 또는 S3 Data Connection 환경변수 모델 파라미터를 읽어오지 못하여 엔진 부팅 실패
YAML: RHOAI 표준 vLLM 추론 Pod 매니페스트 (vllm-serving-pod.yaml) Kubernetes Manifest 
apiVersion: v1
kind: Pod
metadata:
  name: vllm-llama3-serving
  namespace: rhoai-workloads
  labels:
    app: vllm-inference
spec:
  # 1. GPU 노드 배치 및 Taint 회피
  nodeSelector:
    node.kubernetes.io/instance-type: "gpu-worker"
  tolerations:
  - key: "nvidia.com/gpu"
    operator: "Exists"
    effect: "NoSchedule"

  # 2. OpenShift 보안 가드레일 준수 (Non-Root)
  securityContext:
    runAsNonRoot: true
    allowPrivilegeEscalation: false
    capabilities:
      drop:
      - ALL
    seccompProfile:
      type: RuntimeDefault

  containers:
  - name: vllm-engine
    image: 192.168.1.10:5000/models/vllm:v0.6.2
    command: ["python3", "-m", "vllm.entrypoints.openai.api_server"]
    args:
    - "--model=/models/llama-3-8b-instruct"
    - "--tensor-parallel-size=2"
    - "--max-model-len=8192"
    - "--gpu-memory-utilization=0.9"

    # 3. GPU 리소스 (요청과 제한 동일)
    resources:
      requests:
        cpu: "8"
        memory: "32Gi"
        nvidia.com/gpu: "2"
      limits:
        cpu: "16"
        memory: "64Gi"
        nvidia.com/gpu: "2"

    # 4. 볼륨 마운트 (/dev/shm 및 모델 스토리지)
    volumeMounts:
    - name: dshm
      mountPath: /dev/shm
    - name: model-weights
      mountPath: /models

    # 5. 모델 로딩 지연을 고려한 3단계 프로브
    startupProbe:
      httpGet:
        path: /health
        port: 8000
      initialDelaySeconds: 30
      periodSeconds: 10
      failureThreshold: 60  # 최대 600초 (10분) 여유 제공
    readinessProbe:
      httpGet:
        path: /v1/models
        port: 8000
      periodSeconds: 5
    livenessProbe:
      httpGet:
        path: /health
        port: 8000
      periodSeconds: 15

  volumes:
  # PyTorch IPC 통신을 위한 메모리 매핑
  - name: dshm
    emptyDir:
      medium: Memory
      sizeLimit: "16Gi"
  # 모델 가중치 영구 볼륨
  - name: model-weights
    persistentVolumeClaim:
      claimName: pvc-model-weights

2. 640GB SSD 기반 로컬 레지스트리 서빙 아키텍처

========================= [ 전체 인프라 및 레지스트리 토폴로지 ] ========================= [ CPU Node 1 (Master / Bootstrap) ] ──────── (192.168.1.10) ├─ SSD 1 (640GB): OS Root (/) & K8s System (/var/lib/kubelet) └─ SSD 2 (640GB): /data/registry 마운트 └─ [ Podman / Docker Registry v2 / Harbor ] (Port: 5000) │ ├── [인증서] /data/registry/certs (TLS/SSL 자체 서명) └── [이미지 풀] /data/registry/data (640GB 대용량 전용 볼륨) │ │ HTTP/TLS 이미지 Pull (10GbE Network) ▼ ┌─────────────────┬─────────────────┬────────────────────────┐ │ │ │ ▼ [ CPU Node 2 ] [ CPU Node 3 ] [ 2xGPU Worker Server ] (vLLM Pod) (Control/Worker) (Control/Worker) (CUDA 12 / vLLM / PyTorch 20GB 이미지 로드) ======================================================================================
⚠️ 왜 K8s 인-클러스터 Pod 대신 호스트 Podman 독립 실행 방식을 강력 권장하는가?

온프레미스 폐쇄망 환경에서는 K8s 클러스터 자체를 설치(Bootstrap)하기 위해 컨테이너 이미지를 먼저 가져와야 하는 닭과 달걀의 문제가 발생합니다. 마스터 1번 노드의 2번째 SSD에 OS 레벨 Podman으로 독립 레지스트리를 띄워두면, K8s가 완전히 중단되거나 재설치되는 재난 상황에서도 전 노드가 안전하게 이미지를 공급받을 수 있습니다.

3. 단계별 구축 및 클러스터 서빙 실행 절차

1
디스크 파티셔닝 및 전용 경로 마운트 (마스터 1번 노드)

두 번째 640GB SSD(/dev/sdb)를 고성능 XFS로 포맷하고 영구 마운트합니다.

# 1. 2번째 SSD 디바이스 확인
lsblk

# 2. XFS 포맷 및 디렉터리 생성
sudo mkfs.xfs -f /dev/sdb
sudo mkdir -p /data/registry
sudo mount /dev/sdb /data/registry

# 3. 부팅 시 영구 마운트 (/etc/fstab)
UUID=$(sudo blkid -s UUID -value /dev/sdb)
echo "UUID=${UUID}  /data/registry  xfs  defaults,noatime  0 0" | sudo tee -a /etc/fstab
2
TLS 자체 서명 인증서 생성 및 보안 설정

클러스터 내부 통신 암호화 및 신뢰성 확보를 위한 SAN 인증서를 발급합니다.

sudo mkdir -p /data/registry/{data,certs,auth}

# SAN에 마스터 1번 노드 IP(예: 192.168.1.10)를 추가하여 10년 유효 인증서 생성
sudo openssl req -newkey rsa:4096 -nodes -sha256 \
  -keyout /data/registry/certs/domain.key \
  -x509 -days 3650 \
  -out /data/registry/certs/domain.crt \
  -subj "/CN=registry.local" \
  -addext "subjectAltName=IP:192.168.1.10,DNS:registry.local"
3
Podman 기반 Private Registry 가동 및 systemd 서비스 등록

OS 부팅 시 레지스트리가 자동으로 시작되도록 systemd에 등록합니다.

# 레지스트리 컨테이너 구동 (640GB 볼륨 바인드)
sudo podman run -d \
  --name local-registry \
  --restart=always \
  -p 5000:5000 \
  -v /data/registry/data:/var/lib/registry:z \
  -v /data/registry/certs:/certs:z \
  -e REGISTRY_HTTP_TLS_CERTIFICATE=/certs/domain.crt \
  -e REGISTRY_HTTP_TLS_KEY=/certs/domain.key \
  registry:2

# systemd 자동 기동 등록
sudo podman generate systemd --new --name local-registry > /etc/systemd/system/local-registry.service
sudo systemctl daemon-reload
sudo systemctl enable --now local-registry.service
4
클러스터 전 노드(CPU 3대 + GPU 1대) 신뢰 레지스트리 등록
